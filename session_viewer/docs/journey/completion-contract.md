# Build the maintained viewer, one finished subject at a time

The learner builds one cumulative Rust/wgpu program from the first frame to the maintained viewer's production tree and behavior. Use the fewest coherent subject checkpoints and lean code. A subject can take several study sessions; typing time does not justify another tutorial.

The course is not yet a complete reconstruction. Calling the maintained runtime, supplying an unexplained final source dump, or refreshing an inventory cannot establish completion.

## Teaching contract

Every subject has a visible goal, prerequisites and owned files, named source includes, an exact run command, its own observable result, a prediction experiment, and a question with an answer. Explain each concept once. Source code belongs in runnable files, not separately maintained Markdown listings.

Apply finished ownership to existing material too. Correct each implementation in its owning subject; later subjects add modules and declared registrations instead of replacing completed implementations. A supplied support module remains untaught until its named owner explains it. Kernel algorithms stay live dependencies; the completed learner viewer must not depend on the finished `session_viewer` crate.

Archive unused tutorials with stable links and preserve required reconstruction fixtures. Count executable checkpoints when reporting consolidation. Reducing sidebar headings while retaining a rewrite sequence does not reduce the tutorials.

## Required coverage

- Every production file under `session_viewer/src` has a named teaching owner or a deliberate omission with an approved reason. File lists, hashes and source links alone are insufficient.
- The early mathematics subject follows first egui painting: frame, fonts, TeX, atlas, column, matrices, clock, actions, replay, matching and deck errors. The later stage subject follows scene rows, camera, strokes, arrows, markers and loading: geometry, per-frame updates, camera fit, projected labels, spatial motion, the net solve, overlap/deck tests, input, upright phones and loading.
- Existing owners teach current object effects and non-pickable rows; stroke dash phase, trims and curve heads; the shared field-by-field arrow function and device constraint; BRep/curve quality; graph decoding; hierarchy; Matrix display; redraw/publication; backdrop, splat selection and current self-tests.
- The kernel API pages and consuming lessons expose Vector/Color/Line interpolation, Polyline resampling and morphing, and Xform interpolation, with actual implementation and test links.
- Camera units, rebasing and reversed depth; all geometry/display families; stable slots, arena reclamation and instance updates; visibility and picking; commands, controls, panels, history and persistence; clipping, contact, ambient, multisampling, quality and resource lifetime reach the maintained behavior.
- Build configuration, browser startup, deck/font fetch, diagnostics, file maps, performance guidance and extension references describe the current implementation.

## Acceptance evidence

Reconstruct and compile every accepted checkpoint from its canonical source. Run the course's structure, ownership and relevant verification checks. Compare the reconstructed final source with the maintained production tree; the archived lesson-37 comparison is not journey parity.

Verify actual browser behavior using original CAD data: commands, picking, hierarchy, drawing, undo/redo, import/save/reopen, camera navigation and GPU output. Review stage steps at desktop and upright phone sizes. Verify the phone-specific arrow constraint with its recorded device evidence; desktop rendering is not a phone test.

Keep source coverage, compilation, runtime assertions and visual/device evidence distinct. Evidence must identify the tested source and checker. Preserve historical proof without re-signing it for changed source, weakening assertions or hiding outstanding failures.

The strict documentation build and required CI must pass for the published revision. Finish with a concise report of what was added, consolidated, moved or deliberately omitted and why. [Historical evidence](../archived/journey-completion-evidence.md) remains available for its recorded scope.
