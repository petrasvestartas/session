## Why this exists

2026-08-16: loading `scenes/pointclouds3.json` (3 Zagreb Cathedral scans, 10.6M points)
got the Chrome tab killed by the Linux OOM killer — `global_oom`, 234 MB free RAM and
228 kB free swap on a 31 GB machine. The tab was the fattest renderer at 2.37 GB and
Chrome tags renderers `oom_score_adj=300`, so it was the designated victim.

Live re-measurement with the scene loaded: renderer **2490 MB** + gpu-process
**1034 MB** = ~3.5 GB, for a GPU payload of 323 MB. `/proc/<pid>/smaps`:

```
1589 MB  [anon:v8-sandbox]                   <- wasm linear memory
 323 MB  /dev/shm/.com.google.Chrome.NffmD9  <- create_buffer_init #3 (files 1+2+3)
 217 MB  /dev/shm/.com.google.Chrome.nPub2S  <- create_buffer_init #2 (files 1+2)
 111 MB  /dev/shm/.com.google.Chrome.lows0D  <- create_buffer_init #1 (file 1)
```

Every point was materialised **five** times: fetched bytes → decoded proto
(`Vec<f64>` + `Vec<u32>`) → kernel `PointCloud` (`Vec<f64>` + `Vec<i32>`) → f32
`CloudPoint` rows → wgpu's `temporary_mapping` mirror. The last two were retained.

Governing constraint: **wasm linear memory never shrinks.** The 1589 MB is the
high-water mark of transient peaks, not the live set. Design for a bounded peak, not
a small live set.

### `10e374a4` — Lesson 37 code
Seven steps. Measured, two agreeing passes, on the real `.pb` files:

| | 3 scans (10.6M) | 14M scan |
|---|---|---|
| peak before | 839 MB | 1365 MB |
| peak after | **518 MB** | **953 MB** |
| retained before | 735 MB | 954 MB |
| retained after | **411 MB** | **533 MB** |

1. `session_from_bytes_chunked` takes `Vec<u8>` and drops it after `decode` — you
   cannot drop a borrow. −104 MB / −411 MB peak.
2. `lib.rs` captures `nbytes` before the move.
3. Kernel: `proto.colors.into_iter()` — `u32`/`i32` are same size and align, so the
   collect reuses the allocation. −53 / −212 MB. Only load-side
   copy-instead-of-move in the crate.
4. `push_cloud` → `reserve_exact`. `reserve` was doubling the shared table to
   445 MiB for 323 MiB of rows.
5. The point buffer **appends**: `zeroed_buffer` + `queue.write_buffer` at a running
   offset, growth copying the live prefix GPU-side.
6. `Scene::upload_to` uploads then clears the CPU mirror. −323 MB retained.
7. `storage_buffer` off `create_buffer_init`.

Step 7 is invisible to a native replay and is the largest single win.
`mapped_at_creation` makes wgpu keep
`temporary_mapping: OnceCell<Vec<u8>> = actual_mapping.to_vec()`
(`wgpu-29.0.4/src/backend/webgpu.rs:1431`) — a full-size mirror of the table in the
wasm heap, copied into and back out to JS. `write_buffer`'s glue is
`getUint8ArrayMemory0().subarray(ptr, ptr+len)`, a zero-copy view (checked in this
project's own `dist/*.js`).

**Growth is exact, not geometric.** Doubling loses on both axes here — appends are few
and huge, so it wastes 122 MB of buffer *and* has the worse worst-transient (668 MB
vs 540 MB). What it avoids is a GPU-side copy, the one operation that never touches
wasm memory.

### `0f1db9c5` — Lesson 38 code
`CloudPoint` (32 B) becomes two parallel arrays — `array<f32>` positions at 12 B and
`array<u32>` RGBA8 colours at 4 B, both stride-4 in the **storage** address space (the
16-byte-stride rule is a *uniform* rule) — plus a `CloudDraw { base, count, instance }` per
cloud. The per-point `instance_id` retires because `first_vertex` makes `vertex_index`
absolute into the shared buffers and `first_instance` lands on `instance_index`; wgpu only
lowers `instance_limit` below `u64::MAX` for instance-rate *vertex* buffers, and this lane
has none. GPU table 421 → 221 MB at 13.8M, 323 → 162 MB for the three scans. `naga` clean.

### `28c6d7be` — Lesson 39 code
Range-request streaming. Verified against the real file before wiring: `walk_to_coords`
returns `(175, 87570576)`, count **3,648,774** (matches the known count), colours field 4
len 27,237,048 at 87,570,756, first point reads back as `(-4.38796, 2035.38, 891.285)`.

Range rather than `ReadableStream` because split doubles, split varints and split length
headers are risks that exist *only* when data is pushed; 8 MB slices rounded down to whole
points cannot split anything. `fetch_range` refuses anything but `206` — a server that
ignores `Range` returns the whole 411 MB body, silently. GPU comes up first (a streamed
cloud writes into buffers that must already exist), `next_tick()` between slices (warm-cache
promises resolve as microtasks and never paint), empty `queue.submit([])` after each write
(Dawn recycles staging only on a completed serial). `CloudSlot` — a name, a count, an
instance row — is the entire CPU footprint of a 13.8M-point scan.

`trunk build` clean.

## Not in scope, worth raising separately

- `PointCloud::_colors` is `Vec<i32>` — 4 bytes for a 0-255 channel, 221 MB per
  13.8M-point cloud where `u8` would be 55 MB. Three-language API change.
- `colors` is packed **varint** on the wire, which blocks the memcpy fast path that
  `coords` gets free. `bytes` or `repeated fixed32` would fix it — schema change
  across three languages and every `.pb` in `session_data/`.
- `push_cloud` does a bare `coords[i*3] as f32`. Fine for scanner-local millimetres;
  a projected CRS (UTM easting ~500000) quantises to ~0.03 m. Subtract a per-cloud
  f64 origin and fold it into the instance matrix.
- `/tmp` is a RAM-backed tmpfs on this machine and `/tmp/claude-1000` holds ~12 GB of
  lidar downloads. That was the largest single contributor to the OOM and it is still
  resident.
